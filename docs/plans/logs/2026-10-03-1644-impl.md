## P1
- `Sources/polepole/SpawnedChild.swift:SpawnedChild.spawn` / `Sources/polepole/ProcessRunner.swift:ProcessRunner.launchDetached` — 子の終了を回収する仕組みが2つあります。dispatch source（終了イベントの通知）と、`waitForExit` での `waitpid(WNOHANG)` の定期チェックです。ただし定期チェックは `waitForExit` を呼んだときしか動きません。`launchDetached` は `waitForExit` をまったく呼ばず、`run` も timeout→SIGKILL の後で2秒待ってそのまま返ります。そのため `launchDetached` と、`run` で timeout まで行ったケースでは、回収を終了イベント頼みにしています / コメント自身が書いているとおり、`source.resume()` から実際にイベントが登録されるまでの間に子が終了するとイベントは届きません（登録は非同期です）。`spawn` の最後で1回だけ `reap()` していますが、それより後に子が終了するケースは防げません。このとき子は zombie のまま残り、イベントハンドラが `self` を握り続けるので `SpawnedChild` 自体もリークします。`cursor` の CLI はすぐ終了するので、この競合にちょうど当たりやすいです / `SpawnedChild` の中に、子が動いている間だけ `reapQueue` 上で `reap()` を繰り返すタイマーを持たせてください（例: 0.1s から間隔を延ばしていき、回収できたら cancel）。こうすれば、`waitForExit` を呼ぶかどうかに関係なく、取りこぼしても回収できます。`waitForExit` の中の定期チェックは、このタイマーにまとめられます

## P2
- `Sources/polepole/SpawnedChild.swift:SpawnedChild.reap` — `waitpid` が -1 を返すと、errno に関係なく `unknownStatus`（回収済み扱い）にしています / WNOHANG なので起きにくいですが、`EINTR` で -1 が返ると、まだ動いている子を「終了した」と判定します。その結果、本当の終了は回収されず zombie になり、`ProcessRunner.run` は exitCode -1 ですぐ返ります / `EINTR` のときは再試行し、`unknownStatus` にするのは `ECHILD` のときだけにしてください
- `Sources/polepole/ProcessRunner.swift:ProcessRunner.spawnLock` — doc コメント（「pipe 生成〜`process.run()` の間に…」）と、`run` の中のコメント「pipe 生成〜run() を直列化」が、`Process` 前提の表現のまま残っています。さらに `POSIX_SPAWN_CLOEXEC_DEFAULT` を使うようになったので、ProcessRunner 同士が並行して spawn しても、相手の pipe の fd が子に漏れることはもうありません / lock の存在理由がコードと合わなくなっていて、読む人が混乱します / lock を外すか、残すならコメントを「CLOEXEC_DEFAULT で自前の spawn 同士の競合は消えた。`markCloseOnExec` は外部（libghostty）の spawn 対策」と書き直してください
- `Sources/polepole/AppRelocator.swift:AppRelocator.removeQuarantine` / `relaunch` — DEV.md には「外部コマンドは `Foundation.Process` で起動しない」と例外なしで書かれていますが、ここは `Process` のままです。呼ばれるのは `ghostty_init` より前の起動直後で、起動するのも platform binary なので実害はありません / それでも次に grep した人がルール違反に見えて混乱します / `ProcessRunner.run` と `launchDetached` に置き換えるか、DEV.md に「ghostty_init 前の起動処理は対象外」と明記してください
